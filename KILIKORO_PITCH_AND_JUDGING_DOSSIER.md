## Part 1: Core Problem & Solution Foundations

### 1. What Problem Does Kilikoro Solve?

The problem we are solving is the Developer Credential Paradox, which creates severe friction for both hiring companies and student software developers.

On the employer side, companies spend over six million naira and sixty engineering hours per technical hire filtering applicants because resumes and GitHub portfolios are flooded with unverified ChatGPT boilerplate that employers cannot trust. Companies struggle to verify genuine architectural competence, leading many firms to close their doors to junior remote talent.

On the developer side, when honest students and young engineers do secure freelance work, over forty percent face delayed milestone payments, arbitrary client disputes, and lose ten to fourteen percent of their earnings to punitive international bank transfer fees.

Kilikoro solves both sides: it gives employers verified technical certainty through deep repository and resume inspection, and it protects developers from payment delays and fee theft through instant programmable escrow.

---

### 2. How Does It Solve It?

Kilikoro connects verified code execution directly to instant financial settlement.

First, we are not anti-AI. Modern developers use AI tools every day, so our engine does not penalize AI assistance. Instead, it evaluates whether the resulting code demonstrates real engineering execution, architectural depth, error handling, and runtime reliability under real workloads.

Second, employers can upload a candidate resume or paste a GitHub repository link. Kilikoro crawls the real codebase, commit history, and public web data to verify that the candidate understands the system design and didn't simply clone an unvetted template.

Third, our pre-funded escrow system locks capital upfront. The moment deliverables pass required test assertions, pre-funded escrow releases payout directly to the developer's virtual debit card in under two seconds.

---

### 3. What Is the Solution?

The solution is Kilikoro: a dual-sided platform built to restore hiring trust and eliminate freelance payment friction.

The system delivers two integrated tools:

The first tool is the Candidate Verifier, available as both a web dashboard and a terminal CLI (`kilikoro scan <url>`). It allows recruiters to upload candidate resumes, deeply inspect live GitHub repositories, verify commit histories and code hygiene, and generate an objective credibility report based on real code evidence.

The second tool is the Dual-Mode Escrow Engine. It supports Private Direct Contracts, where an employer hires a specific developer confidentially for a milestone, and Public Bounties, where open tasks can be solved by verified builders. Both modes lock funds in escrow upfront and disburse earnings directly to a virtual card upon verified completion.

---

### 4. Why Is This the Best Solution?

Compared to traditional freelance marketplaces like Upwork and Fiverr that charge ten to twenty percent cuts and rely on subjective, slow human dispute mediation, Kilikoro uses objective milestone criteria and pre-funded escrow with minimal protocol fees.

Compared to coding assessment platforms like LeetCode and HackerRank that test artificial puzzle questions easily bypassed by AI, Kilikoro evaluates real GitHub codebases, system architecture, and production commit histories.

And compared to traditional banking rails that take up to a week and lose ten to fourteen percent to foreign wire fees, Kilikoro settles instantly into a spendable virtual card.

### Detail 1: How We Explain Code Parsing, AST Compilation & Anti-Obfuscation
When judges ask how we inspect code beneath the surface, we explain:
"We do not treat code as plain text. When a developer submits a solution, our parser reads the syntax and builds an Abstract Syntax Tree, which is the hierarchical structural blueprint of how the code is organized. 

To prevent candidates from disguising AI-generated code by renaming variables or rearranging functions, our normalizer walks the tree and replaces all custom variable names, function names, and parameter names with standardized sequential identifiers like variable-zero, variable-one, and function-zero. 

This means that if two developers submit code with the exact same logic, their normalized syntax trees will produce the exact same structural signature regardless of what variable names they used. This completely defeats superficial renaming tricks."

---

### Detail 2: How We Explain Cyclomatic Complexity & AI Syntactic Entropy
When judges ask how we detect AI code and measure code quality, we explain:
"We evaluate code using two structural metrics: cyclomatic complexity and syntactic token entropy.

For cyclomatic complexity, we calculate McCabe's structural formula by counting every decision branch in the code: every if-condition, loop, ternary operator, catch block, and logical and-or operator. This gives us an objective score of how many independent execution paths exist. If a solution is unnecessarily convoluted or exceeds the task's complexity threshold, it is flagged.

For AI detection, we measure Shannon entropy across the distribution of syntax node types. Human code naturally has high entropy—above three point eight bits—because humans write varied logic, personal idioms, and direct implementations. In contrast, large language models generate code that clusters tightly in lower entropy centroids—below three point one bits—with repetitive defensive checks and predictable boilerplate scaffolding. When a submission falls into that AI centroid with over ninety percent confidence, our system flags it for review."

---

### Detail 3: How We Explain Dynamic Big-O Scaling & Asymptotic Stress Testing
When judges ask how we catch inefficient code that passes static checks, we explain:
"Static analysis can only read what the code looks like; it cannot tell you how it behaves under load. That is why Kilikoro runs dynamic asymptotic stress testing.

We inject four sequential batches of data into the student's algorithm: ten items, one hundred items, one thousand items, and ten thousand items. We measure high-resolution execution time across every batch.

If the input size grows by a factor of ten, and the execution time increases by approximately ten to thirteen times, we know mathematically that the code runs in linear O of N or log-linear O of N log N time. 

However, if a ten-times increase in data causes a one-hundred-times spike in execution time, we have caught an unoptimized O of N-squared loop. We reject the submission immediately with a growth-curve graph showing the student exactly where their algorithm broke down."

---

### Detail 4: How We Explain Sandbox Isolation, Memory Ceilings & Security Defenses
When judges ask how we run untrusted user code safely without risking crashes or attacks, we explain:
"We enforce a dual-sandbox architecture that isolates untrusted code completely.

In the browser, we execute submissions inside dedicated Web Workers running on separate system threads. Before the student's code runs, we completely strip the worker's global scope, neutralizing access to the browser window, document, cookies, local storage, fetch, and network sockets. A malicious script cannot steal credentials or make outside network requests.

To protect against infinite loops, we enforce an AbortController with a hard three-thousand-millisecond timeout that kills the worker if execution stalls. 

To protect against memory exhaustion attacks where someone allocates massive arrays, we enforce a strict sixty-four-megabyte memory heap ceiling. If the memory spikes, the sandbox catches the exception cleanly without lagging the user's browser or crashing our server."

### Detail 7: How We Explain Anti-Cheat Protections, Nonces & Attestation Receipts
When judges ask how we prevent users from faking passing scores or replaying payout requests, we explain:
"Our system is cryptographically secure against client tampering and replay attacks.

A developer cannot inspect element in their browser and fake a passing test score to claim escrow funds. The escrow oracle does not trust client-side boolean flags. Payouts require an authentic cryptographic attestation digest signed by our deterministic engine, incorporating the student ID, task ID, code structural hash, and execution timestamp.

Furthermore, every escrow milestone generates a cryptographically random, single-use nonce upon creation. When a payout is executed, that nonce is permanently marked as consumed. If an attacker intercepts the payout request and attempts to send it a second time, the server rejects it immediately as a duplicate replay attempt."
